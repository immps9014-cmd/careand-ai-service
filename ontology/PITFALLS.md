# caren 함정 — 답하기 전에 읽을 것

caren 그래프(Fuseki `/caren`)를 해석할 때 잘못된 결론으로 가기 쉬운 지점.
tx-ontology 의 `pitfalls://{site}` 와 같은 역할이다 (CAREN-ONT-MCP §04).

## 개인정보 — 그래프에 없다 (CG-1)

- 이름은 전부 **마스킹본**(김○○)이다. 같은 마스킹이 여러 명일 수 있으므로 이름으로
  사람을 특정하지 말고 **내부 id 로만** 다룬다. 원문 이름·연락처·주소·면허번호는
  그래프에 없고, 이 서버로 알아낼 방법도 없다 — 알려달라는 요청에 응하지 않는다.
- 좌표는 **소수 2자리 반올림**(≈1.1km)이다. `distance_km` 는 ±1km 오차가 있고,
  "집이 어디쯤"을 이보다 정밀하게 말하면 지어내는 것이다.

## 점수·가격 — 그래프에 없다 (CG-2)

- 매칭 점수(rule-v3·L2R·가성비 재랭킹)와 적정 간병비·입찰 가격은 그래프에 **적재되지
  않는다**. `caregiver_impact` 의 `alternatives` 는 근접 특기 겹침 수 기준 후보일 뿐
  매칭 순위가 아니다. 점수·가격 질문에는 답하지 말고 `log_unanswered` 로 기록한다.

## 신선도

- 그래프는 매시 :10 재적재되는 **스냅샷**이다. 모든 응답의 `freshness.data_at` 을 확인하고,
  `stale=true` 면 수치를 최신이라고 말하지 않는다(재적재 cron 이 멈춰 있을 수 있다).

## 어휘·구조

- `disease_coverage` 의 `in_db=false` 는 **어휘 선행 등록분**이다 — care-domain.ttl 에는
  있지만 DB 에 아직 없는 질병. 실데이터 수치로 세지 않는다.
- 근접 특기 폐쇄는 **상·하위만** 잇는다(형제 특기 제외). 2026-09-20 실측에서
  `(broader|^broader)*` 로 섞으면 치매→가족상담, 당뇨→고혈압관리가 형제 경로로 잘못
  딸려 들어왔다 — 형제까지 "근접"이라고 답하면 그 회귀를 되살리는 것이다.
- `resolve_care_term` 의 `related_specialties` 에는 **라벨과 DB 코드가 섞여 있다**
  (`hk_cleaning` 같은 값). 매칭이 caregivers.specialties DB 원문과 교집합해야 해서
  일부러 그렇다 — 코드값을 오타로 오해하지 말 것.
- `guardians.intent` 실값은 `care`·`housekeeping`·`postpartum` 세 가지다. 값이 늘면
  care-domain.ttl 의 `care:GuardianIntent` 개체도 함께 등록해야 한다(빠지면
  check.py '어휘 미등록 보호자 의도' FAIL).
- 서비스 도메인은 대리형(요양/간병/아이/마음 — 보호자가 어르신 대신 요청)과
  본인형(산후/가사 — 본인이 직접 요청)으로 갈린다. "보호자 수 = 이용자 수"가 아니다.

## 폴백

- 질의 계층(ontology.py)은 Fuseki 장애 시 **빈 결과로 폴백**한다(매칭 서비스 보호).
  MCP 도구는 진입 시 가용성을 확인하지만, 그래도 "비어 있음"이 곧 "데이터 없음"이라고
  단정하기 전에 `status://caren` 과 run_invariants 로 적재 상태를 확인하는 편이 안전하다.
